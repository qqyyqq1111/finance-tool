## 二、v1.0 MVP 批次拆解

> **排期原则**：每批次结束时产品必须处于"可运行"状态（可打开、可演示、不破坏既有功能），即时 git 提交。

### 批次①：项目骨架 + 数据层

| 项 | 内容 |
|----|------|
| **功能清单** | ① index.html 应用骨架（Tailwind CDN、移动端优先布局、底部Tab导航：明细/记一笔/结算/看板/设置）② `js/db.js` LocalStorage 封装（统一 key 前缀、CRUD、schema版本号、数据导入/导出JSON）③ 数据模型初始化（见07-PRD字段定义）④ 身份切换（模拟双人：切换"查看人"） |
| **交付物** | 可打开的多Tab空壳应用 + 数据层单页自测按钮 |
| **验收标准** | 刷新页面数据持久；导出JSON可重新导入还原；身份切换后界面正确显示当前人 |
| **依赖** | 无 |

### 批次②：记账 + 三层隐私架构（核心卖点）

| 项 | 内容 |
|----|------|
| **功能清单** | ① 记一笔表单（金额/收支类型/分类/归属人/日期/备注/隐私层级三选一：公开·单笔私密·存入小金库）② 账目明细列表（按月份分组、按当前查看人过滤）③ 三层隐私过滤逻辑（Layer1公开→所有人可见；Layer2单笔私密→非本人仅见"1笔私密支出"占位；Layer3小金库→非本人完全不可见，余额也不可见）④ 小金库独立账户视图（仅本人可见） |
| **交付物** | 完整记账流 + 隐私过滤演示 |
| **验收标准** | 切换身份后：对方私密单笔不可见内容但可见条数；小金库账户与明细完全消失；本人视角全部可见；分类统计同步过滤 |
| **依赖** | 批次① |

### 批次③：分摊结算引擎（核心卖点）

| 项 | 内容 |
|----|------|
| **功能清单** | ① 分摊规则设置（默认5:5，支持自定义比例/按类别覆盖）② 月度结算计算（共同支出按比例分摊，各自实付 vs 应付 → 垫付差额）③ 结算页（本月谁该给谁多少钱 + 逐笔构成明细）④ 历史结算记录（确认后锁定当月） |
| **交付物** | 规则设置 + 月度结算页 |
| **验收标准** | 构造多笔不同归属/比例的账目，结算金额与手工核算一致；含小金库的支出不参与共同分摊（小金库默认个人支出，除非标记为公开） |
| **依赖** | 批次② |

### 批次④：仪表盘 + 设置 + 备份

| 项 | 内容 |
|----|------|
| **功能清单** | ① 看板（本月收支汇总、分类占比、双人收支柱状对比、结余）② 分类管理（预置餐饮/房租/交通/购物/娱乐/医疗/人情/其他，支持增删）③ 数据导出（Excel/CSV）+ JSON备份/恢复 ④ 免费版/会员版解锁开关（模拟商业化分层）⑤ 关于页（隐私说明、免责声明） |
| **交付物** | v1.0 完整版 |
| **验收标准** | 看板数据与明细页合计一致；导出文件可打开；切换"免费版"后双人/隐私/结算功能入口隐藏 |
| **依赖** | 批次③ |

### 批次⑤（v1.0 收尾）：联调 + 发布

数据加密开关（Web Crypto 选型落地）、边界用例自测、README、部署 GitHub Pages、打 tag `v1.0.0`。

## 四、Git 迭代规划

### 4.1 仓库结构

```
finance-tool/
├── index.html              # 应用入口（单页）
├── css/                    # 自定义样式（Tailwind CDN 之外的少量补充）
├── js/
│   ├── db.js               # LocalStorage 封装 + 数据模型
│   ├── privacy.js          # 三层隐私过滤（纯函数，可单测）
│   ├── ledger.js           # 记账业务逻辑
│   ├── split.js            # 分摊结算引擎（纯函数，可单测）
│   ├── dashboard.js        # 看板渲染
│   ├── settings.js         # 设置/导入导出/身份切换
│   └── app.js              # 路由与页面装配
├── docs/                   # 产品文档链（本目录）
├── test/                   # 纯函数单测（privacy.js / split.js / db.js）
├── .gitignore
└── README.md
```

### 4.2 分支策略（单人简化流）

```
main        ── 稳定可运行版本，仅接受 feature 分支合并，合并即打 tag
 └ feature/批次名-功能名   ── 每个"可演示的小步"一个分支
```

- 单人项目不设 dev 分支，避免管理成本；
- `feature/*` 分支存活不超过一个批次；完成后合并回 main 并删除；
- 紧急修复：`hotfix/*` 从 main 拉出，合并后同样打 tag。

### 4.3 Commit 规范（Conventional Commits）

```
<type>(<scope>): <中文描述，动词开头，50字内>

类型：feat 功能 | fix 修复 | docs 文档 | style 样式 | refactor 重构 | test 测试 | chore 杂务
scope：db | privacy | ledger | split | dashboard | settings | ai | docs
```

示例：

```
feat(privacy): 实现三层隐私数据过滤，小金库对非本人完全隐藏
fix(split): 修复按类别覆盖比例时垫付差额为负的计算错误
docs(mrd): 竞品分析v2.3审阅意见落实
```

### 4.4 版本标签规则（SemVer）

- `v1.0.0`：v1.0 MVP 全批次完成并验收；
- `v1.x.0`：新功能批次合入（如 `v1.1.0` = AI记账上线）；
- `v1.0.x`：bug修复；
- 每次打 tag 附 release note（功能清单 + 已知问题），沉淀为作品集"版本演进记录"。

### 4.5 迭代流程（每批次固定节奏）

```
1. 建 feature 分支
2. 开发（小步提交，每完成一个子功能即 commit）
3. 自测（对照本批次验收标准逐条勾选）
4. 合并 main → 打 tag（若为批次收尾）
5. 更新 00-交接总览 的"已完成工作"一节
```

## 五、验收基线（全版本 DoD）

任何批次完成需满足：

1. 浏览器直接打开 index.html 即可用（无控制台报错）；
2. 移动端（375px宽）布局不错位；
3. 所有数据操作刷新后持久；
4. 隐私过滤用例全过（三层级 × 双身份切换矩阵）；
5. 不引入任何用户数据外发请求（AI功能启用后仅限脱敏解析请求）。

## 六、风险与回滚

| 风险 | 缓解 |
|------|------|
| LocalStorage schema 变更破坏旧数据 | db.js 内建版本号+迁移函数，每次结构变更版本+1 |
| 批次间功能互相污染 | 每批次独立分支，合并前对照验收清单 |
| 开发中断 | 批次粒度小（1-2天级），任何批次边界都是可交付状态 |
| Tailwind CDN 依赖网络 | 首屏加载需联网一次，后续浏览器缓存；v2.0 PWA 时本地化资源 |
