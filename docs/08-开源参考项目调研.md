> **文档版本**：v1.0

> **文档性质**：开发动工前的开源可复用性调研结论；回答"是否有现成代码可直接复用"及"从哪里借鉴什么"

## 一、结论先行

1. **不存在可"大部分直接复用"的项目**：技术栈吻合（纯静态+vanilla JS+LocalStorage）的项目全是个人记账或聚会AA；功能最贴近双人财务的项目全部带后端/框架。
2. **推荐策略**：移植 MIT 算法（分摊结算）+ 借鉴数据模型/schema + 复用同栈 PWA 骨架片段 + **三层隐私过滤自研**（无现成实现，这正是本项目差异化价值所在）。
3. **双人场景算力红利**：通用 Splitwise 债务简化算法在双人场景退化为"算一次净差额+一笔转账"，实现成本极低；通用贪心算法留待未来"项目型分账"（装修/旅游）时再引入。

## 三、三项关键调研结论

### 3.1 分摊算法参考实现（按优先级）

1. **首选 spliit**（MIT，活跃）：分摊模式枚举+债务简化，逐行翻译；
2. 算法文档：rajgupta04（greedy）、JW-Albert（双指针中文说明）；
3. ⚠️ node-splitwise-js 无 license，只能看思路；
4. **关键认知**：贪心法=按净余额排序、最大债务人↔最大债权人循环配对；纯双人场景只需 `balance[m1] = paid[m1] - share[m1]`，一笔转账即完成——与 07-PRD 6.2 节算法一致，可直接对照 spliit 验证边界（尾差、比例和≠100等）。

### 3.2 local-first 数据层设计

- **架构思想**：actual —— 余额永远由流水推导，不冗余存储（本项目07-PRD数据模型已符合：无余额字段，统计实时计算）；
- **落地 schema**：gizbar 的 gatherings/members/expenses/payments + ZyPLJ 的记录字段（id/date/amount/type/category/description）；
- **演进预留**：kudilog 的 schemaVersion 版本化导出（07-PRD 的 fc_schema_version 同思路）。

### 3.3 多用户隐私视图过滤（本项目核心，需自研）

最接近的4个实现均不完整：

| 项目 | 可套用机制 |
|------|-----------|
| fiscus-Ai-finance | 同一浏览器多用户 localStorage 键空间隔离 + 口令哈希 |
| shared-expense-book | nameSelector.html 身份选择器 UI |
| SpendTrail | multi-profile 切换 |
| ezbookkeeping | 个人/家庭二级账户可见性分层（概念同构） |

**自研要点**（已写入07-PRD）：每条记录带 `privacy: public|private|vault` + `ownerId`，渲染层统一经 `privacy.js` 单一过滤函数裁剪；**vault级记录建议加密存储**（WebCrypto口令派生密钥），否则三层隐私只是UI假象——此项列入 v1.0 批次⑤加密开关的实现重点。

## 四、落地建议（开发执行清单）

1. **先抄schema后写引擎**：数据层融合 gizbar 结构 + fiscus 键命名空间 + ezbookkeeping 账户分层；分摊引擎对照 spliit 移植；金额一律以"分"存整数（Splitwise类项目经典坑）；
2. **License红线**：MIT/Apache（spliit、SpendTrail、ZyPLJ、ezbookkeeping、gizbar、fair-split、fiscus）可复用代码；AGPL（cowallet）与无license（node-splitwise-js、1024house等）只看设计；借鉴致谢写入"关于"页；
3. **PWA骨架参考 SpendTrail + ZyPLJ**：与本项目技术栈完全一致（无构建、原生SW+manifest），缓存策略可直接借用；坚决不引入React/Vite构建链；
4. **LocalStorage两个硬伤提前避**：①5MB容量+单设备孤岛 → 第一天就做JSON导入导出+schemaVersion（已列入批次①/④）；②vault不明文存 → WebCrypto对称加密（批次⑤）；
5. **为v1.1 AI记账留口**：参考 kudilog 的"一行式自然输入"与 fiscus 的可选AI集成——先写本地规则解析器，Kimi API 做增强兜底，保持"纯静态可用、AI增强可选"。
